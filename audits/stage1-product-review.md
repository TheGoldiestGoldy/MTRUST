## Coding benchmark: what the numbers do and do not mean

**Verified scope:** scripts/CoreSyntheticBenchmark.java:18-37 and :67-115 constructs one straight line of **0, 64, 512 synthetic rails**, no sidings/routes/vehicles/players, calls Simulator.sync(), and times Simulator.tick(). It creates scratch directories, stops/reloads and checks **only the rail count**. scripts/benchmark_tsc.py:23-26 hash-locks the JAR; :69-74 uses Xms128m/Xmx512m and 2 logical active processors; :161-203 generates unique scratch roots and output CSV/JSON. Good discipline for **synthetic core API regression**, not evidence of Minecraft operational behavior.

**Methodological weaknesses independently found:**
- Java harness lines 76-95 and 90-94 set synthetic time to **System.currentTimeMillis()-1000 before every call**. Candidate Simulator.java:170-189/:352-363 computes wall-time catch-up and calls its inner tick. This is a repeated approximately-one-second catch-up, **not a continuous, deterministic 40-second simulated trip** and not one 50-ms Minecraft server tick. It has wall-clock and tick-branch dependence. The exact released Simulator.tick() is the executable reference; candidate source illustrates but does not prove byte-identical logic.
- 'Warmup 12' is **12 invocations, not 12 seconds**. Raw warmup_wall_seconds around **0.23-0.31** include JVM startup/setup; the field cannot be advertised as controlled warmup seconds. Short invocations may be influenced by JIT, scheduling and background load; the 8-sample reviewer run is only a functional smoke.
- **RSS/PSS sample-phase contamination:** Python sampler lines 82-101 polls after WARMED until subprocess exit, while Java lines 106-116 performs save, constructs a second Simulator/reload and sleeps **350 ms AFTER emitting RESULT**. The tick loops are sub-millisecond, so substantial samples can represent save/reload and post-work idle rather than the 40 timed ticks. No per-sample phase/timestamp exists to cleanly separate them. T2 per-process RSS samples range approximately **90-185 MiB**; the pooled 174 MiB is not a train-tick steady-state, native-memory attribution, or controlled peak. Re-instrument before using it for capacity decisions.
- Used/committed heap are **one snapshot per process before save**; committed is 130 MiB, not total Java heap upper bound. Thread allocation covers the main thread only; BufferPoolMXBean direct memory is not all native memory. GC time is collection time total, not pause p95/p99. 512 simple rails cannot represent dense routes/stations, MTR client draws, multiple players or a normal Fabric process.
- There is **no control with MTR absent**, no active S1-S4, no full-game JVM/OS baseline, no properly optimized-Java comparison, no JFR/NMT native accounting, no MSPT/TPS, and no repeatable causal attribution for a server's RAM use. A nearly 0 ms result from a topology-only tight loop is not grounds for Rust.

## UI investigation: evidence and alternatives

**Verified:** static renderer map includes MainRenderer -> RenderVehicles/RenderRails/RenderPassengers and texture tick; NewOptimizedModel has a GPU buffer. Released WorkerThread's bounded discard path exists. **Plausible, NOT profiled:** unculled per-car transforms, redundant objects, excessive draw/uniform submissions, rail callbacks and texture churn. **Unsafe inference:** class-local absence of a Frustum symbol means no downstream/backend culling; one bytecode draw call site means one draw per train; a successful model-cache class check means bounded VRAM. Render-stage grouping and static buffers already exist, so introducing another identical cache without trace evidence is likely wasted work.

**NOT MEASURED:** metrics/ui-baseline.csv contains five scenario placeholders and no captured frame samples; there is no render-thread or GPU frame-time median/p95/p99, 1% low, actual GL draw count, GPU buffer upload rate, GPU RAM, allocations/s, train/car count, or fixed-camera shader ON/OFF comparison. VSync=true and maxFps=60 in inspected existing settings are confounders, not an explanation of reported drops. Shader/Iris/Sodium, chunk loading, rail count and Distant Horizons activity are independent competing causes. Isolated tests need same-rail S0 and train-dense S3, front/back camera, and shader controlled A/B, plus non-MTR control, fixed quality/resolution and actual GPU/CPU split.

**Frame analyzer limitation reproduced:** ui_frame_stats.py:20-36 accepts 100 timestamp rows in reverse order and reports a plausible 99-second duration; with 120 rows containing one NaN timestamp it silently uses 119 frames. It validates frame_ms but not finite/monotonic capture time or contiguous capture duration. 1% low is **1000 / arithmetic mean of slowest ceil(1%) frame durations**; a legitimate defined convention, not universal between tools. This is a medium-severity tool-validation gap, not proof of a real game FPS problem.

## Data integrity, feature parity and rights

**High-confidence released-JAR risk:** FileLoader bytecode calls Files.newOutputStream with an **explicit CREATE option**, without a TRUNCATE_EXISTING option, and has a Files.deleteIfExists parse-error branch. A synthetic JDK21 check writing 'XY' over an existing 'ABCDEF' file with CREATE-only produced **'XYCDEF'**, proving shorter writes can retain a stale tail under this API. This is an API-level corruption **hazard**, not evidence any production save was corrupted. Candidate FileLoader.java:142-151 also appears to update file hash and 'filesWritten' even after a write exception; verify that control flow directly against released bytecode before escalating to a confirmed flaw. No existing world or save file was opened for this review. Existing original MTR should not be 'repaired' on production through an untested write.

**Compat status, independent of labels:** MTR mod id and bytecode type presence = **PASS for identification only**. Generated MessagePack 0/64/512 rail-count reload = **PARTIAL**. Real save unknown fields/schema/ordering, atomic migration and rollback = **NOT TESTED**. Actual packet wire bytes, C2S/S2C ordering, addon binary ABI/mixins/registries, resource packs, shader visuals, train interiors/glass/lights, riding/driving GUI, passenger behavior, translations, client/server join and Fabric boot = **NOT TESTED**. Metadata of 100 client and 82 server mod JARs is an inventory, NOT a compatibility run; absence of declared mtr dependency does not exclude reflection or hard-coded classes.

Upstream MTR and TSC MIT code notices do not automatically cover nested Elementa/UniversalCraft/Kotlin distributions or **4,436 assets/mtr ZIP entries**, models, fonts, resource packs, shader integrations and their license obligations. No third-party assets should be copied until their rights and attribution are recorded. World save writer, rollback proof and deployed fallback require different safety gates. No native Rust implementation or candidate optimized-Java control exists.

## Rust feasibility and G1 prerequisites

Changing simulation implementation to Rust does **not** remove Java's Fabric shell, game/world heap, renderer or GPU work; JNI adds boundary CPU cost, marshaling, ownership/threading hazards and **native RSS**. The core may be a minor fraction of the total memory; Java heap improvement is not proof of lower process RSS/PSS. A server-core rewrite is an especially weak proposed remedy for measured **client-renderer** frame drops. First show a causal Java/core hotspot versus shader/world and a plausible native advantage over simple Java data-structure/index/queue/cache fixes.
