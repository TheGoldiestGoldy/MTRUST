# Stage 1 UI optimization plan | candidate work only, not Stage 2

**Scope:** investigation and future validation priorities; **no implementation authorized or performed**. These five candidates rank by plausibility and verified release structures, **NOT by measured FPS gain**. They must be profiled, baseline-compared and Product-Reviewed before code changes. Never drop quality, render distance, shader effects, interior detail, signs, controls or addons as a substitute for fixing a hot path.

| Priority | Proposed change, contingent on measurements | Expected technical mechanism, NOT a predicted speedup | Risks / mandatory proof |
|---|---|---|---|
| **P1** | **Safe per-car view-frustum/AABB filtering**, separate render-only visibility decisions from car simulation/interaction; include near-plane, riding, long cars, curves and bounds from every moving part | Fewer offscreen mesh submissions and shader draws when facing away from trains. Released renderer verifies distance-helper calls, candidate uses per-car radial test, but no class-local frustum reference | Camera inside/near train must never disappear; retain sound/door/interior/collision logic; compare 360-degree turn with fixed scene, count bounds tested/draws saved; prove correct visibility for moving cars and transparent parts |
| **P2** | **Reduce per-frame vehicle/car/passenger allocation:** preallocate/recycle temporary lists/transforms, memoize passenger render data by ID with lifecycle invalidation; avoid redundant smoothing work when not needed for visible rendering | Reduce render-thread GC and CPU work. Confirmed beta Random/RemotePlayer allocation call sites and candidate stream/collect/lambda/boxed pairs | Dynamic passenger changes, resource reload, multi-car movement, player skin and riding alignment; validate JFR allocations and no desync, never incorrectly skip simulation |
| **P3** | **Batch or instance only compatible buffered mesh draws:** reuse identical GPU mesh resources and render-layer binds, consider driver-safe GPU instancing for same texture/stage/shader state with per-instance transform/light data, without changing visual features | Lower CPU-side draw/uniform submission overhead where model part count × visible cars is high; existing GPU buffers already cached (do not duplicate this work) | Iris shader uniform ABI and Sodium pipeline, alpha sorting/translucency, emissive light, custom car variants, door animation, resource pack shader; only implement following actual draw-call/GPU timestamp evidence and parity captures |
| **P4** | **Cache eligible rail segment geometry using topology/style/versioned keys**, invalidate on edits and sign changes; split moving/dynamic overlays from static rail mesh | Avoid repeated railMath/segment callback construction unrelated to actual train count. Beta has AABB distance check; candidate still emits eligible rail segments per render | Creative rail building, curves, custom rail textures, animated signals, node previews and boundaries; compare same S0 rail scene before/after, track CPU frame-time and invalidations |
| **P5** | **Audit dynamic texture cache and worker queue lifecycle:** bound per-frame expiry work, track texture bytes, generation/deletion and GL uploads, fix dropped-job marker state if reproducible; investigate buffer disposal on model reload | Reduce frame scan work, texture generation stalls/VRAM churn and stuck placeholders without reducing pixel quality | CJK/font and station text correctness, PIDS, route maps, matrix/layout, scrolling displays, texture ID reuse, shader layer cache, thread ownership. Unit stress test overflow/reload then original vs candidate screen parity |

## Priority-to-evidence mapping

- **P1:** exact RenderVehicles binary calls CullingHelper.getDistanceFromCamera and contains no explicit frustum token in its own javap output; source candidate RenderVehicles.java:64-126 builds car properties then radius-culls mesh draws. Other downstream culling is unknown.
- **P2:** released bytecode has java.util.Random constructor and new net.minecraft.class_745 in passenger renderer; candidate RenderVehicles.java:64-85 and :309-321 builds per-frame objects. Actual execution frequency and cost are unknown.
- **P3:** exact NewOptimizedModel bytecode has VertexBuffer upload and draw references; MainRenderer invokes begin/render; candidate MainRenderer.java:305-324 submits each model transform separately after grouping. We know static buffers already exist; **draw-call count is not measured**.
- **P4:** exact RenderRails calls CullingHelper.getDistanceFromCameraToBox; candidate RenderRails.java:251-348 regenerates rail callbacks. Rails may be a stronger cause of dense-station cost than trains.
- **P5:** exact DynamicTextureCache.worker dispatch/creation/tick methods; candidate WorkerThread.java:158-182 drops queued items on overflow, DynamicTextureCache.java:290-365 maintains generating flags. Verify the binary queue flow explicitly before filing a bug or implementing a fix.

## Experimental order and acceptance gates

First (without any renderer modifications) make a new generated-world test client with original MTR and controlled synthetic S0/S1/S2/S3 train counts. Hold resolution, draw/render distance, graphics quality, camera, rail topology, resource pack/model, weather, time and tick path fixed. Compare shader OFF/ON and front-facing/away separately. Record frame-time median/p95/p99 and 1% low, CPU render-thread scopes, JFR allocation, actual GPU time/draw calls/texture uploads, RAM/RSS/VRAM and driver utilization over >=3 independent runs. Store raw data, duration, warmup, clocks, tools and uncertainties. Include a non-MTR control to isolate shader/vanilla chunk work and Distant Horizons network/LOD activity.

Then test **only one hypothesis at a time** in an independent branch and test profile. Each optimization requires: (1) measurable incremental reduction on the target bottleneck beyond run-to-run noise, (2) no material regression to S0 or shader-off, (3) exact visual/interactivity parity including train interiors, animated doors, lighting, third-party model packs, multiplayer passengers and driver/rider controls, (4) compatible Sodium/Iris and original client/server packet behavior, (5) heap/RSS/VRAM comparisons including reload and cleanup, and (6) independent Product Review and PM approval. No fixed speedup threshold is invented; thresholds come from a captured baseline.

**Stop condition for this audit:** publish hypotheses and reproducible static evidence only. **NOT IMPLEMENTED / NOT MEASURED**: frustum optimizations, instancing, geometry deduplication, cache changes, client profiling or Rust renderer. No merge, production deployment or Stage 2 work.
